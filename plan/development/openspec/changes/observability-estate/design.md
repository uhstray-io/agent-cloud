## Decisions

1. **Ship in dependency order.** First inventory and baseline evidence, then local metrics discovery and correlation, then provisioned alerts with a delivery drill, then traces. This follows `PRINCIPLES.md` §7 and prevents trace storage from preceding basic failure detection. Alternative rejected: deploying Tempo with the first metrics change.
2. **Use declaration-based collection within a host, generated targets across hosts.** Alloy already has the local Podman socket for logs, so it also discovers opted-in metrics targets and forwards their samples to Prometheus on the private o11y network. Prometheus does not receive an engine socket. Alloy joins the service network and addresses targets by container name and declared port; the pilot must prove DNS and scrape reachability, since labels alone are not proof. Pinned Alloy v1.5.1 lacks newer network-selection settings, so the config reuses its existing discovery component. A target on another VM is outside that socket; its endpoint and permitted route come from inventory and a generated scrape fragment. Neither path asks an operator to hand-edit `prometheus.yml` per service. Alternatives rejected: a second engine socket bind in Prometheus, and assuming local discovery covers remote VMs or isolated Compose networks.
3. **Normalize identity at collection.** Container name is the stable `service` label, matching `PRINCIPLES.md` §7. Keep `container` as a compatibility label for existing Loki dashboards; add `service` without replacing it until dashboards migrate. High-churn containers are dropped by a relabel rule. Alternative rejected: rename the existing Loki label in place.
4. **Keep provisioning declarative.** Grafana reads dashboards and alert rules from committed files. Ansible retrieves notification material from OpenBao and renders only gitignored, owner-readable runtime files. The alert delivery drill is an explicit Semaphore workflow. Alternative rejected: UI-created contact points or alert rules.
   The selected Discord bot credential is a provisioning input, not a Grafana contact-point URL. A Dev-bound Semaphore playbook reads it from OpenBao, requires the private guild and text-channel IDs, reuses its own named webhook on retries, and writes only that webhook URL to the o11y OpenBao record. A foreign or duplicate webhook name fails closed. The destination remains a private inventory declaration; no channel or token value enters the public repo.
   The local fault drill marks the last Discord message before creating its probe and requires a newer message from that webhook naming the failed service. It keeps bot credentials and message bodies out of task output and removes only the probe it created.
   The paused baseline creates a dependency: the existing drill refuses until the rule is active, while persistent alert enablement must wait for a delivery receipt. Resolve this with a Dev-bound, local-only canary workflow. It verifies the exact checkout and an initially paused rule, checks Discord history and OpenBao credentials before activation, then reuses normal OpenBao-backed rendering to activate only a rule filtered to its unique disposable probe. It runs the named fault and message-receipt checks, then restores paused rules and removes the contact point in an Ansible `always` path. Missing-telemetry rules stay paused during the canary. Restoration uses the existing `.env` and declarative paused Grafana templates, removes the webhook line, and verifies the restored state without requiring OpenBao to remain available. A separate idempotent Dev-bound restore template covers abrupt controller interruption, when Ansible cannot execute `always`. A failed restore blocks promotion. Persistent enablement remains a separate reviewed configuration change after the canary receipt; the canary must not leave an enabled inventory flag behind.
   Production extends this same reversible workflow without an engine-socket dependency: a uniquely labelled, unreachable static target is rendered into Prometheus's mounted scrape directory, then Grafana's probe-filtered rule is activated with the OpenBao-backed contact point. The receiver must already be deployed at the exact reviewed Dev revision; the drill never switches its checkout. The canary adds only the OpenBao-backed webhook line to the existing runtime environment and removes only that line during restoration, preserving all other settings without a second secret file. The drill waits for the named `up=0` series, Grafana firing, and a newer message from the owned Discord webhook. Its `always` path removes the generated scrape file, restarts the declared stack, and verifies the paused, contact-free baseline; the interruption-recovery template converges the same state. The file name is fixed and the playbook refuses to overwrite an existing file before it mutates anything. A normal production deploy refuses an unfinished canary and directs the operator to the restore workflow. Production inventory keeps persistent alerts disabled until this receipt passes.
5. **Set budgets before expansion.** Inventory controls retention and a target series ceiling. The pilot records series count and storage growth before enabling remote targets or Tempo. The eventual Tempo receiver has real downstream consumers and a bounded block retention; a listener with no consumer is excluded.
6. **Integrate committed work without changing its checkout.** The clean production inference telemetry branch is merged into this isolated branch. Its DGX jobs are inventory-generated and optional; local discovery is additive. Review the combined diff and test it before local deployment.
7. **Validate the branch that will be reviewed.** The existing local Semaphore repository record is mounted from the main checkout, so its successful run cannot validate this feature branch. Use a declared, separate repository/template binding or equivalent isolated local Semaphore mechanism; never repoint the shared record. Verify the exact revision used by the task.
8. **Treat production receipt as the finish line.** The approved read-only audit included `grafanapodman`, but Semaphore cannot reach it and its data cannot be classified. Provision a dedicated, declared receiver through NetBox, Proxmox, private inventory, and Semaphore after the local alert gate; do not reuse, delete, or repoint the legacy host as part of that work. Verify the new receiver's storage, network and SSO boundary, then query named DGX and agentgateway series/log labels. Keep GPU collection disabled until the DGX owner proves the exporter and approved access path.
9. **Use the right OIDC path for each environment.** Local Grafana can exchange tokens with `authentik-server` on its shared container network. A production receiver on its own VM uses the declared `auth.<zone>` Caddy HTTPS endpoint for token and userinfo calls; the deploy refuses an absent or local-test production zone before placing files. Enable Grafana in the production Authentik app catalog and declare its Caddy/DNS route before testing login. Alternative rejected: carrying the local container hostname or `:8443` URLs into production.

## Risks / Trade-offs

- [A mounted engine socket grants powerful API access even with a read-only bind] → constrain it to the o11y collector, review engine permissions, and never expose it over TCP.
- [Labels exist but the collector cannot route to a service] → require a live target query in the onboarding gate and name unreachable endpoints.
- [An alert only proves Grafana evaluated a rule] → run a delivery drill and confirm receipt at the configured destination.
- [A drill fails after temporarily activating the contact point] → use an `always` restore, verify paused rules and contact-point removal, and refuse promotion if restoration fails.
- [The local Semaphore template executes the main checkout] → create an isolated branch binding and record the task revision before calling a local run valid.
- [A remote scrape job exists but its endpoint is unreachable] → gate production on inventory, firewall, target-UP, and Loki receipt checks; name the failing source.
- [An unreachable legacy Grafana host contains data that a new deployment overwrites] → keep its inventory and storage untouched; deploy the new receiver on a separately declared VM and reconcile legacy data only after access is restored.
- [Historical plans describe future components in the present tense] → add dated, evidence-backed as-built notes without deleting the original design rationale.
