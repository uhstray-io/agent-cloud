## Context

The current stack has Prometheus, Loki, Alloy, Tempo, and Grafana. The service overview uses Docker container names, while remote metrics and OTLP logs already use a `service` hint. Grafana rules notify the Discord contact directly. An open estate-wide instrumentation change inventories future producers, but its signal contract and profile budget need a concrete baseline.

## Goals / Non-Goals

Goals: one bounded service identity, honest cross-signal coverage, a private profile backend with a measured opt-in pilot, and alerts routed with stable context and restrained repeat cadence. Preserve state and keep deployment reproducible from `dev` through Semaphore.

Non-goals: instrumenting every service in this change, replacing the alert policy tree, introducing Grafana Cloud IRM, importing the Docker LGTM demo image into production, or forcing profiling on workloads without a supported producer and budget.

## Decisions

1. **Identity contract.** Use `service` as the Prometheus/Loki/alert key and `service.name` in OTLP traces; map profiles to a stable `service_name`. Local Compose identities use `<project>/<service>` to distinguish reused names; remote targets use declared service values. `cluster` and `environment` are inventory-bounded. `owner` and `severity` are alert labels. Keep instance and container details as drill-down context, not routing dimensions. Maintain an explicit allowlist of low-cardinality fields and a test for forbidden dynamic labels.
2. **Visibility.** Change the service overview selector from `container` to `service`; use declared metrics targets for a missing-telemetry view and show logs independent of container naming. Retain the existing Loki-to-Tempo derived field. Add a bounded cardinality/ingestion panel from collector self-metrics and verify the query against live metric names before claiming runtime acceptance.
3. **Profiling.** Add Pyroscope to the existing Compose stack with an isolated persistent volume and internal-only port. Add the Grafana datasource. An Alloy `pyroscope.scrape` and `pyroscope.write` pipeline is enabled only for a verified in-stack pprof producer through inventory. Use a small initial retention/resource budget and explicit measurement before other runtimes join. A normal deploy never calls the clean workflow. The source-level candidate preflight validates disabled/enabled rendered configs and bounded isolated Alloy component loading only. It uses the deploy-shared metric-label vars, passes only the five validated numeric scrape limits read from the running Alloy container, and requires API evidence of the existing scrape component in both candidates plus profile absence/presence as appropriate. Candidate logging is disabled. The dedicated Dev-bound acceptance operation reruns the candidate and current budget checks, requires same-run private-inventory provenance, pins the reviewed controller and deployed receiver revisions, and compares the disabled rendered config with the current bind-mounted file. It checks the fetched Semaphore metadata for one production inventory, one template for this playbook, and the expected repository, then binds the template's inventory ID to that unique production record. The imported provenance survey separately requires `observed` and `exact_bytes_match` for that same fetched production inventory; the ID remains inside the `no_log` validation and is not added to the survey receipt. This proves the configured binding, but not which template launched the current invocation; no trusted task-ID environment variable is available, so ambiguous duplicate same-playbook templates are refused. Immediately before writing the enabled config through that file's existing inode, the operation captures an activation Unix-second; it reloads Alloy and requires a positive Pyroscope timeline sample at or after that second for `service_name="o11y/alloy"`. The profile read uses the fixed internal Pyroscope render URL through `podman exec o11y-grafana wget -q -O -`, retaining bounded command output and timeout. SIGTERM/SIGINT are deferred while cleanup restores the disabled config, reloads Alloy, and checks a positive post-disable timeline sample using the same activation boundary; a pending signal yields a sanitized failure receipt. SIGKILL or host power loss may stop the process before cleanup. A post-disable query failure is reported only after positive initial sampling/delivery. The receipt's post-disable result does not claim durable storage across a Pyroscope restart. The operation reports success only when all `o11y-*` container identities/mounts and all named-volume metadata match their pre-run snapshots. Dev-bound task 5842 returned an unavailable receipt with sampling/delivery unverified, restored disabled, post-disable query unverified, and reason `post_disable_query_not_observed`; that reason overwrote the initial `profile_not_observed` failure. A separate bounded read-only Grafana datasource-proxy query for the same profile and pilot window returned HTTP 200 with seven positive CPU timeline samples, without proving the operation's initial query succeeded. Keep task 2.3 open until reviewed live acceptance proves sampling, delivery, and post-disable query, with durable storage across a Pyroscope restart separately proven.

4. **Alerting.** Keep the existing Discord contact. Add stable labels, dashboard/runbook annotations, and rule-level `notification_settings` grouping/timing. Expected-target alerts use one deterministic multidimensional rule per stable `(service, environment, cluster)` group, with a UID derived from that tuple; refuse collisions against declared targets, other provisioned rules, or a previously owned group identity. Each rule's PromQL expression is an exact OR of its declared `(job, instance, service, cluster, environment)` selectors, and resulting series retain their job and instance labels. Escape dynamic Grafana `$labels` references as `$$labels` in provisioned rule labels because Grafana applies environment interpolation when reading those labels. Grafana 11.4 adds `alertname` and `grafana_folder` to group-by keys, so a single rule title per stable group is required for same-service target failures to share a notification group. Preserve the old per-target UIDs as paused, UID-qualified tombstones during migration. A rollback to per-target rules must explicitly tombstone every active group UID before reactivating legacy target UIDs; reverting source alone is unsafe because Grafana retains omitted provisioned UIDs. Do not file-provision the shared policy tree, whose replacement semantics could overwrite unrelated routes. Read back rule labels, annotations, duration, pause state, and routing settings, then run a bounded delivery drill. The active production drill injects two same-service loopback targets and requires both instance-specific service-down alerts plus exactly one owned Discord message containing both instance details and the service dashboard link. Live grouped delivery remains pending.
5. **Estate adoption.** Amend the open estate-wide instrumentation plan with a per-service signal/label/profile/owner declaration and a phased capacity gate. Service onboarding references that contract. Avoid duplicating source truth in dashboard JSON or a second inventory.
6. **Production retention capacity.** Target Prometheus 90d, Loki 45d, and Tempo 1080h (45d), but preserve the existing 15d / 7d / 168h effective values until measurement is complete. A production retention tuple that differs from that approved baseline requires a nonzero Prometheus size cap and a numeric ID referencing a separately reviewed successful capacity receipt before any deployment write. The ID is only a reference and does not establish capacity by itself. The receipt remains unavailable until a private receiver-host collector provides at least seven days of CPU and memory history and per-backend stored-byte growth, the forecast retains at least 30% free disk and 25% memory headroom with CPU p95 below 70%, and any guest growth path is idempotent with backup before resize. The budget verifier reports only current guest root filesystem and memory observations; root filesystem usage is not treated as the observability-volume forecast.
7. **Receiver-host measurement source.** Add a dedicated node_exporter container on the private o11y Compose network with no published host port, host PID, a read-only host-root mount, and only CPU, meminfo, root-filesystem, and load collectors. Alloy receives no host-root mount. A same-host source is proven by private-network membership and no published port; REMOTE exporters still require source-scoped firewall proof. Local mode skips host-versus-guest parity checks because Podman runs inside its VM. Only production retention expansion resolves each named volume from its exact running-container destination, verifies the Podman volume mountpoint, and requires at least 30% free on each backing filesystem before config or image changes. For a clean first production deploy, the gate validates Podman's `store.volumePath` from `podman info --format json` as an absolute existing directory and measures its backing filesystem, where the named volumes will be created; it does not assume guest `/` and Podman storage share a filesystem. The separate read-only budget receipt uses `podman unshare du` for rootless stored-byte measurement and remains fail-closed on partial or ambiguous volume state. Ordinary deploy and recovery are not blocked by the expansion gate. Clean-deploy rejects a nonbaseline retention tuple before destructive cleanup. These observations and the collector’s runtime readback do not replace the seven-day history and measured capacity forecast.
8. **Scoped Grafana MCP credential and client permissions.** The user requested a production `mcp-grafana` service account with the Grafana Editor role and a no-expiration token. This is the documented production exception to PRINCIPLES.md's read-only-by-default Grafana MCP policy, limited to this dedicated account; the existing o11y liveness watcher's separate Grafana service account remains Viewer. Reviewed Semaphore automation keeps OpenBao as the token source of truth and installs a mode-0600 local client copy at `~/.config/mcp-grafana/prod.token` without logging the token. A Grafana account's Editor role and the MCP client's exposed tools are separate permission controls. The user explicitly authorized production write tools, and automatic approval review approved installation of the tested launcher. The installed production profile selects OpenBao `mcp_grafana_token` without `--disable-write`; the local profile retains `--disable-write`. Ten installed-path tests passed. Permission/config implementation is complete; an installed production launcher handshake remains a separate pending acceptance gate.

## Risks / Trade-offs

- A new Pyroscope process and volume consume memory and disk; production enablement is gated on measured VM headroom, retention, and one verified sample. A local config check alone does not prove an end-to-end profile.
- A service selector derived from Prometheus cannot enumerate log-only services. The dashboard must state this scope, while Logs Drilldown remains available for log-only producers and the estate inventory records coverage gaps.
- Grouping delays delivery by the configured wait period. The delivery drill must allow for that delay and verify both firing and resolution.
- Adding indexed labels increases series and stream counts. Establish baseline and compare before broad rollout; reject unbounded values at the collector or producer boundary.
- Longer retention can exceed the receiver's storage capacity. A current root filesystem observation is not a forecast; keep the capacity receipt absent until the private host source, seven-day backend growth evidence, and guest growth/backup procedure are verified.
- `node_exporter` host PID/rootfs behavior under rootless Podman and the exact root-filesystem parity check must pass through Semaphore before the metric source is accepted; a container start alone is insufficient. Volume bytes are read from only the five named backend containers' destinations and must match `podman volume inspect` mountpoints.
- Production verifier task 1789 passed its retention, scrape-limit, and active-series checks without changing the approved 15d / 7d / 168h values; its guest-root free space was below 30%, and it did not resolve named volume backing filesystems. This is diagnostic evidence only, not a capacity receipt.

## Migration Plan

1. Land the spec and code from an isolated branch after one independent review and green CI; merge into `dev`.
2. Run the normal non-destructive Semaphore deploy from `dev`, verify five existing components plus Pyroscope, data sources, dashboard, alerts, and preserved volumes.
3. Enable one verified profile producer only after measuring VM headroom and checking privacy; confirm a profile in Grafana and record ingestion/cardinality deltas.
4. Expand service onboarding in batches under the estate-wide change; size the VM from measured load before enabling high-volume producers.

Rollback: disable the pilot and restore the prior reviewed config through `dev` and Semaphore. For expected-target alerting, render a UID-qualified paused tombstone for each grouped rule UID before restoring per-target rules; verify all group and target UIDs through live readback so no omitted provisioned rule remains active. Preserve all named volumes for a separate retention decision.
