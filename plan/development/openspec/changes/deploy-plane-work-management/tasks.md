## 6. Forge Discord Plane app

The app receives interactions over the Discord Gateway and answers them over Discord's HTTP interaction callback. It does not answer them through the Gateway.

- [ ] 6.1 Create the service `platform/services/plane-discord/`, a Python container. Its image is built to GHCR by a workflow modelled on `.github/workflows/build-honcho.yml`. The libraries `discord.py` and `plane-sdk` are approved dependencies. Joseph A. Wisneski IV approved them on 2026-10-23, and their versions are pinned at implementation time.
- [ ] 6.2 Implement the Plane-app bot-token flow with client credentials, using the OAuth endpoints confirmed in 0.13.
- [ ] 6.3 Implement the webhook receiver. It computes HMAC-SHA256 over the raw request body bytes, in the digest encoding confirmed by 0.15, and compares it with `X-Plane-Signature` in constant time. A request that does not verify is refused, and nothing is posted. The receiver is reachable only on the internal network from Plane. A verified delivery is leased under task 6.5, posted to the per-project channel that site-config declares, and marked posted only after Discord accepts it.
- [ ] 6.4 Manage the webhook secret. Capture the secret when the Plane webhook is created, through the code path that 0.7 identified, and store it at `secret/services/plane:discord_webhook_secret`. The app reads it through a shared read. To rotate it, regenerate the secret in Plane through that code path, store the new value, and redeploy the app. Regenerating the secret invalidates the old one immediately.
- [ ] 6.5 Deduplicate deliveries without losing one. Key on the event identifier that 0.15 showed is stable across retries, in a persistent store on the app's own volume. Take a `pending` lease with a unique-key insert before posting, mark it `posted` only after Discord accepts the post, and on a failed or timed-out post release the lease and answer Plane with an error so Plane retries. A `posted` id is never posted again; an unexpired `pending` lease answers a concurrent delivery with an error; an expired lease from a stopped process counts as released.
- [ ] 6.6 Implement the slash commands `/plane create`, `/plane assign` and `/plane status`. The app receives each `INTERACTION_CREATE` over the Gateway. It responds through the HTTP interaction callback, `POST /interactions/{id}/{token}/callback`, within 3 seconds. When the work will take longer than that window, it sends a deferred acknowledgement through the same callback endpoint, and completes the reply afterwards. Source: `https://docs.discord.com/developers/interactions/receiving-and-responding`.
- [ ] 6.7 Authorize the mutating commands. `/plane create` and `/plane assign` run only for a Discord user who holds a Discord role declared in site-config and who appears in the site-config mapping from Discord user id to Plane workspace member. The app performs the write with its bot token and records the mapped Plane member in the work item, as a comment or activity. An unauthorized or unmapped invocation is denied with an ephemeral reply, and makes no Plane write. `/plane status` is not gated this way.
- [ ] 6.8 Implement link previews for `KEY-123` and for work-item URLs. Link previews need the privileged `MESSAGE_CONTENT` intent. Enable it on the Bot page under Privileged Gateway Intents, which is available without verification for apps under 10,000 users. Without it, `content` is empty except for mentions and direct messages. Requesting an intent that is not enabled closes the Gateway with code 4014. Source: `https://docs.discord.com/developers/events/gateway`.
- [ ] 6.9 Read the bot token from `secret/services/discord:bot_token` through shared read. Do not copy it. Record the blast radius in the service's `CLAUDE.md`: the app is one more long-lived holder of the platform bot token.
- [ ] 6.10 Write `deploy-plane-discord.yml` and its template. The app deploys as its own composable service on the Plane VM. The deploy is idempotent. Its verify step checks that the Gateway session is up, which is how a missing intent from 6.8 fails the deploy. Running the deploy a second time converges: it changes nothing, creates no duplicate resources, and does not redeploy Plane.
- [ ] 6.11 Verify locally, subject to risk 8. A signed webhook event posts to a test channel, `/plane status` answers through the HTTP callback, and a work-item link unfurls.
- [ ] 6.12 Validation gate: scenario "Signed event posts to the project channel" holds. Its companion scenarios "Unsigned event is refused", "Redelivered event is not posted twice", "Status command answers through the HTTP callback", "Unmapped user cannot create a work item", "Unmapped user cannot assign a work item", and "Discord thread messages are not mirrored into Plane" are also checked in 6.11.
